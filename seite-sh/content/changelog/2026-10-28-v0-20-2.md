## Password access: path tricks refused

The Cloudflare Pages Worker that `[access]` generates checked a decoded request path against the protected prefixes, then handed the original request to the static asset server. A path with an empty segment, such as `//members/secret.md`, did not match the `/members` prefix, so it was treated as public; if the asset server collapses the doubled slash, the protected file was served without a password. The Worker now answers `400 Bad Request` for paths with empty segments (`//`, so a doubled slash anywhere on a password-protected site is refused), for paths that still contain an encoded `/`, `\` or `.` (`%2F`, `%5C`, `%2E`) after a decode at any depth, and for paths whose further decoding would land on a different route, in addition to the backslashes and `.`/`..` segments it already refused. Protected prefixes now match regardless of case (`/Members/x` is protected like `/members/x`). Rebuild and redeploy sites that use `[access]`.

## `seite skill remove` stays within the pack

`seite skill remove <pack>` deleted every file listed for the pack in `.claude/.seite-skill-packs.json`. That manifest is part of the project, so a cloned repository could list other files, including absolute paths, and have them deleted. Remove now deletes only regular files the pack itself installs (its agents, commands, skills and scripts), never through a symlink, and leaves anything else in place with a warning. Files in `context/` are kept, as the message has always said. Removing a custom skill accepts only a plain skill name, never a path. `seite skill install` and `seite skill update` refuse to write when a target file or directory (the manifest, `context/`, `.claude/agents/`, `scripts/seo/`, …) is a symlink or sits behind one, so a cloned repository can't redirect those writes outside the project.
